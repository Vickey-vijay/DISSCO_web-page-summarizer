# Conclusion

Version 2 summarizes the page a reader has open with a small language model that runs inside Chrome, on the laptop's own graphics card. Version 1 sent the page text to Google's Gemini service and needed a key. Version 2 needs no key and no account, and the page text stays on the computer. The internet is used once, for the first download of the model. Most of the project was reused from Version 1: reading the page, cutting long text into parts, merging the part summaries, the popup, and the background job that keeps running when the popup closes. The new parts are the offscreen page that holds the model, the WebLLM library that runs it, the engine that connects the two, the graphics-card check, and the setup scripts.

The project was tested at three levels. The 65 unit tests check the logic of each piece without a browser. The 26 browser tests load the extension in a hidden Chromium and press the real button, with a pretend model that can be made to fail on purpose. The 14 Windows checks run the batch files in throw-away copies. Real-model runs measured the actual model on the developer's laptop, which has an NVIDIA RTX 3050 and a built-in Intel chip. In the clean runs, a first use on the NVIDIA chip took about 197 seconds, most of it the download and the warm-up. A short article with the model already stored took 15.3 seconds with no internet. The built-in Intel chip, which the extension handles with a smaller model, took 199 seconds for a short article on first use and wrote at 4 to 5 tokens a second.

The main lessons are practical. A library's default storage can fail inside a particular kind of extension page, so each feature has to be tested in the page that uses it. The same laptop can run the model about thirty times faster or slower depending on which chip Chrome chooses, so the speed has to be measured on the path the client will use, and the screen has to say which chip is in use. A value from the browser, such as the vendor name, is data and needs converting before a reader sees it. A cleanup step has to cover every write that could still be running. Each of these lessons came from a fault that a test or a real run exposed, and each fault is recorded in chapter 15.

The honest state of the work has three parts. The software works in a test browser on one laptop, and the failure cases are covered by tests. The client's laptop is untested, because its details have not arrived, so the client's speed, model choice and disk margin are still [to be measured]. The answers of the small model have faults that matter to a reader: the prompt's marker text can appear at the start of a summary, labels from the prompt are copied into the output, one saved summary gives a wrong date, and some bullets say nothing. The memory the model holds while loaded has not been measured. The visible-browser check and the graphics switch on a real Chrome are still to do.

The next step with the most value is the client's laptop. Its graphics chip decides which of the two paths applies: the separate card, which writes tens of tokens a second, or the built-in chip, which needs the small model and waits minutes for each summary. The repair of the prompt markers and the answer format comes next, because those faults are the ones a reader would notice first. Version 2 is a working local version with its limits written down, and what remains is to test it where the client will use it.
